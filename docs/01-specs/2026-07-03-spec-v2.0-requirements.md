# v2.0 需求规格 — 产品重构为轻量化双版本

> 创建时间：2026-07-03
> 状态：讨论阶段
> 关联讨论：2026-07-03 会话

---

## 一、背景与动机

当前 v1.0 产品（PySide6/Qt + FunASR 本地模型）安装包约 2GB，核心问题是"太重"：
- FunASR Python 运行时 + PyTorch 依赖占用大量空间
- 用户需要本地 GPU/CPU 资源进行 ASR 推理
- 不符合用户最初期望的"轻办公会议软件"定位

## 二、产品分版本规划

### C 版（To C，个人/轻量级）

**定位**：面向个人用户和轻量级办公场景的会议录音转写工具

**核心要求**：
1. 安装包极小（目标 < 50MB）
2. ASR 转写通过云端 API 完成（不依赖本地 GPU）
3. 说话人分离通过云端 API 完成
4. **声纹匹配本地执行**（CAM++ via ONNX，企业共享 API key，员工无需注册账号）
5. AI 摘要通过云端 API 完成
6. 双轨录音（本地+系统音频）能力保留
7. 离线时仅能录音，不能转写

**不需要的功能**：
- 离线 ASR 转写
- 本地声纹嵌入提取（改为 ONNX 推理）

### B 版（To B，企业级）

**定位**：面向对数据安全、保密有要求的企业

**核心要求**：
1. 服务端部署在企业内部服务器
2. 模型放在企业内部服务器
3. 客户端对接企业内部服务器 API
4. 数据不外流
5. 企业统一管理音色库
6. 客户端类似 C 版，只对接服务端

**服务端技术选型**：
- FunASR Server（OpenAI 兼容 API）
- 可选 vLLM 加速
- Docker/K8s 部署

## 三、功能需求（C 版优先级）

### P0 — 核心功能（必须实现）

| 功能 | 说明 |
|------|------|
| 录音 | 麦克风 + 系统音频双轨录音 |
| 云端 ASR 转写 | 通过 API 调用云端 ASR（MiMo/讯飞/腾讯云） |
| 云端说话人分离 | 通过 API 返回说话人编号 |
| 本地声纹匹配 | CAM++ ONNX 本地推理 + 本地音色库余弦匹配 |
| AI 摘要 | 云端 LLM API |
| 转写结果格式化 | Markdown/TXT/JSON/SRT 等多格式导出 |

### P1 — 重要功能

| 功能 | 说明 |
|------|------|
| 企业 API Key 管理 | 管理员配置 key，员工无感使用 |
| 声纹库本地管理 | 新增/编辑/删除声纹，与 v1.0 一致 |
| 双轨合并 | 本地时间戳对齐合并 |
| LLM 纠错 | 云端 LLM 修正 ASR 错字 |

### P2 — 增强功能

| 功能 | 说明 |
|------|------|
| 剔除无效发言人 | 划线标记而非删除，总结时过滤 |
| 自动检测系统音频 | 需重新设计方案（固定时间窗口方案被否决） |
| 跨设备声纹同步 | 未来考虑 |

## 四、非功能需求

| 维度 | 要求 |
|------|------|
| 安装包大小 | C 版 < 50MB（含 CAM++ ONNX 模型 ~30MB） |
| 启动速度 | < 3 秒 |
| 转写延迟 | 云端 API 响应时间 + 网络延迟 |
| 部署方式 | C 版：独立安装包；B 版：Docker + 客户端 |
| 跨平台 | C 版优先 Windows，未来考虑 macOS/Linux |
| 数据安全 | B 版数据不出内网；C 版音频上传云端 |

## 五、用户原始设想记录

### 轻量化思路
> "现在的软件太重了，并不是我最初期望的轻办公会议软件"

### 双版本架构
> "分两个大版本，分别to C和to B"
> - C版：云端模型为主，软件本身只需录音
> - B版：服务端+客户端，模型放企业内部服务器

### 企业共享 Key 场景
> "私营企业对保密性要求没那么高，使用C版产品，企业买某一个平台的token plan，员工共用一个企业账号的不同或相同API key就能实现会议记录功能"

### 功能完整性
> "现在能实现的功能未来两个版本一定要全部实现的"

### 剔除无效发言人
> "把要剔除的人的发言划线划掉，但是不直接删除，总结时忽略划线内容"
> - 放在 SpeakerDialog 中
> - 每个说话人增加"剔除"toggle
> - 底部增加"重新总结"按钮

### 自动检测系统音频
> "线下和线上协同会议时，有可能出现线下讲很久中途增加线上成员的情况"
> - 固定时间窗口检测方案被否决
> - 需重新设计持续监控+动态切换方案
> - 暂不实施

### UI 框架选择
> "为了流畅性和最终实现效果，这两个版本可以完全抛弃现有架构和开发语言，要找最合适的架构去实现"

### 工作节奏
> "这是个大工程，未来一段时间我们都是方案阶段，不用做具体的实现"
